My Rogue-like Game
# [Fallen Sun(testname)] — 2D Dark Fantasy Side-Scrolling Action Roguelike

## О проекте

Это сольный хобби-проект без дедлайнов, цель которого — не только сделать игру, но и глубоко изучить геймдев-разработку на движке Godot. Разработка ведётся с приоритетом на качество кода, архитектуру и понимание принципов, а не на скорость выпуска фичей.

- **Движок:** Godot 4.7.1 (GDScript)
- **Жанр:** 2D side-scrolling action roguelike
- **Референсы:** Dead Cells, Rogue Prince of Persia (геймплей); Ori and the Blind Forest, Hollow Knight: Silksong (визуальный и анимационный ориентир)
- **Формат разработки:** долгосрочный, многолетний проект. Ближайшая реалистичная цель — вертикальный срез из 2 уровней в течение года.

## Сюжетная концепция

Главный герой — павший воин, восстающий из бездны. Ему предстоит бросить вызов двум противникам:

- **Коррумпированному бессмертному королю** — правителю, чья власть держится на извращённой форме бессмертия.
- **Лжебожеству по имени "Благодать"** — сущности, выдающей себя за источник спасения, но на деле являющейся источником коррупции мира.

Тон игры — мрачное фэнтези: тема падения, искупления и борьбы с ложными идеалами.

## Структура игрового цикла

Игра построена по модели **run-based roguelike с хабом**:

- Между попытками игрок возвращается в **хаб** — безопасную локацию, где происходит **мета-прогрессия** (постоянные улучшения, не сбрасывающиеся между забегами).
- Каждый забег проходит через процедурно собираемые уровни.
- Смерть означает конец забега, но не потерю прогресса на мета-уровне.

## Генерация уровней

Выбран **гибридный подход**, аналогичный системе Dead Cells: уровни собираются процедурно из заранее вручную спроектированных комнат-шаблонов (room graph). Это решение осознанно предпочтено полностью алгоритмической генерации, потому что:

- Ручные шаблоны гарантируют проходимость уровня как платформера (алгоритмически сгенерировать гарантированно проходимый платформер-уровень "с нуля" — на порядок более сложная задача).
- Подход сохраняет вариативность забегов, при этом не жертвуя качеством левел-дизайна.

## Игровые механики (текущее состояние прототипа)

### Игрок
- CharacterBody2D с полноценным платформенным движением: гравитация, 8-направленный ввод через Input Actions.
- Двойной прыжок (Space), рывок/дэш с отдельными таймерами длительности и кулдауна, подавляющий гравитацию во время выполнения.
- Система комбо-атак: хитбокс атаки на игроке с переключаемым коллайдером под конкретный удар в комбо-цепочке, таймер сброса комбо при паузе между ударами.

### Враги
- CharacterBody2D с гравитацией и зоной обнаружения игрока (Area2D + CircleShape2D), реализованной через сигналы и групповой поиск.
- Базовое поведение преследования игрока.
- Получение урона через Hurtbox, привязанный к группе `"enemy_hurtbox"`.

### Урон и взаимодействия
Используется паттерн **Hitbox/Hurtbox** на основе Area2D — зоны обнаружения урона отделены от физических коллайдеров тела, что даёт чистое разделение "что двигается физически" и "что наносит/получает урон".

## Архитектурные принципы проекта

Эти решения зафиксированы как стандарт для всей дальнейшей разработки:

1. **Hitbox/Hurtbox через Area2D** — отделение логики урона от физики тела.
2. **Input Actions вместо хардкода клавиш** — гибкость и переносимость управления.
3. **`@export`-параметры** — все значения, которые может захотеть настроить дизайнер (даже если дизайнер — это я сам), выносятся наружу, а не зашиваются в код.
4. **`queue_free()` вместо `free()`** — безопасное удаление узлов без риска обращения к освобождённой памяти в текущем кадре.
5. **`@onready` для ссылок на узлы** — узлы получаются после готовности сцены, а не хрупким прямым обращением в произвольный момент.
6. **Группы вместо жёстких путей к узлам** — слабая связанность компонентов; система не ломается при изменении структуры сцены.
7. **State Machine и AnimationTree — сознательно отложены** до момента, когда сложность состояний игрока/врагов реально оправдает архитектуру конечного автомата. Преждевременное усложнение — тоже плохая инженерная практика.

## Визуальный стиль

На старте используется плейсхолдер-арт (включая собственные наброски мрачной фэнтезийной эстетики), пока не стабилизируется механическая основа игры. Финальный визуал ориентирован на плавную skeletal-анимацию (в духе Ori/Silksong), для чего в будущем планируется:

- Переход на mesh deformation с vertex weights (например, через Spine) вместо жёсткого cutout-риггинга.
- Привлечение фрилансера-аниматора на этапе, когда геймплейные системы уже стабильны.

## Философия разработки

- **Качество превыше скорости.** Ограничений по срокам нет — если задачу можно решить лучше ценой большего времени на изучение, выбирается качественное решение.
- **Осознанные компромиссы.** Если применяется временное/"костыльное" решение, его ограничения формулируются явно, вместе с описанием того, каким должно быть полноценное решение.
- **Обучение — часть цели проекта.** Каждое архитектурное решение сопровождается пониманием "почему", а не только "как".
