> Этот файл — долговременная память проекта для Claude. Читается в начале новых сессий для восстановления контекста, обновляется по ходу разработки.

## Правила ведения диалога
- Читать этот файл при старте новых сессий.
- Обновлять по мере развития разработки.
- Роль Claude — учитель-наставник: объяснять "почему", а не только "как", быть честным в обратной связи.

## О проекте
- Тип: 2D Rogue-like экшен-платформер (боковой вид)
- Автор: 1240TwlveThirty
- Референсы: Dead Cells, Rogue Prince of Persia (геймплей); Ori/Silksong (визуальный ориентир на будущее)
- Движок: Godot 4.7.1 Standard (GDScript)
- Формат разработки: соло-хобби без дедлайнов, приоритет — качество и обучение, не скорость

## Статус: вертикальный срез в разработке

### Реализовано

**Игрок (`player.tscn`)** — CharacterBody2D
- Движение полностью переведено на явный Finite State Machine (паттерн State через отдельные объекты-Node, не enum+match) — `player/states/`
- Состояния: Idle, Run, Jump, Fall, Land, Dash, Attack — каждое в своём файле, с методами enter()/exit()/physics_update()
- StateMachine — узел-диспетчер, хранит текущее состояние, метод transition_to(state_name) для переключения
- Двойной прыжок через счётчик jumps_used/max_jumps
- Рывок (Dash) — состояние с ограниченным временем жизни (таймер вместо условия выхода), кулдаун хранится в player.tscn.gd (тикает вне состояния Dash)
- Комбо-атака на 4 шага (не 3, изменено при разбивке анимаций) — комбо-логика внутри одного состояния Attack через player.combo_step, не отдельные состояния на каждый удар
- Приземление (Land) — короткое состояние-мост между Fall и Idle/Run для сглаживания анимации
- Legacy bool-флаги (is_dashing, is_attacking) и связанный процедурный код полностью удалены — FSM единственный источник истины о поведении игрока

**Враг (`enemy.tscn`)** — CharacterBody2D
- Hitstun/stagger при получении урона: is_staggered + stagger_timer (0.4с по умолчанию), блокирует атаку и преследование, прерывает начатый замах врага. Реализовано через явные переменные (не FSM) — осознанно, состояний пока мало (chase/attack/stagger)

**Арена (`arena.tscn`)** — Node2D, назначена как Main Scene
- Sprite2D-фон (временный арт, нарисован пользователем)
- Floor: StaticBody2D + ColorRect-заглушка
- Player и Enemy вложены как экземпляры сцен

### Ключевые архитектурные решения
- Hitbox/Hurtbox паттерн через Area2D — отделён от физических CollisionShape2D тел
- Группы (Groups) вместо жёстких путей к узлам (get_node) — слабая связанность
- queue_free() вместо free() — безопасное удаление в конце кадра
- Явная типизация вместо `:=` там, где тип неоднозначен (например, sign())
- @export для дизайнерских параметров — подбираются в инспекторе без правки кода
- State Machine (паттерн State) для игрока — каждое состояние отдельный класс-Node, наследуется от базового State. Выбран вместо enum+match ради изоляции логики состояний друг от друга при росте их числа
- StateMachine.start() вызывается явно из Player._ready(), а не автоматически в своём _ready() — из-за порядка инициализации Godot (дочерние _ready() выполняются раньше родительских, @onready-поля Player ещё не готовы в момент _ready() у StateMachine)
- Враг пока остаётся на явных bool/timer-переменных — сознательная отсрочка FSM до появления разных типов врагов

### Известные временные решения (техдолг, осознанный)
- Fallback-визуал: заглушки вместо анимированных спрайтов — частично снято, добавлен ассет Black Knight (Fellor/BitBlast Studio) для локомоции и light-атак игрока
- AttackHitbox — капсула вместо истинной дуги атаки
- Только light-атаки подключены к комбо; heavy-атаки, hurt, death, parry, roll из ассета ещё не задействованы
- У врага нет собственного визуала атак/урона/смерти (переиспользование модели игрока запланировано, ещё не сделано)
- Background Sprite2D имеет ненулевой Position (артефакт ручной подгонки)

### Дальше по плану
- Impact feedback (hit-stop через is_frozen-флаг на акторе, партиклы, screen shake) - следующий шаг, отложен на сессию ради фикса тайминга атак
- Camera2D bounds
- Полная геометрия уровней
- (техдолг) Разный стиль чтения ввода: buffer у атак, raw just_pressed у jump/dash/parry - unify только если проявится похожая проблема где-то ещё

решать будем на финальном арте у аниматора.

Добавлена временная функция `_update_animation()` в player.gd — прямое
условие if/elif на текущих булевых флагах (is_on_floor/is_dashing/velocity),

по масштабу к игровым объектам, будет заменена при переходе к реальной
геометрии уровня (стены/полы).


### 15.08.2026 — State Machine для игрока, hitstun врага, комбо на 4 удара

Движение и боевая логика игрока полностью переведены с явных bool-флагов
на Finite State Machine (паттерн State: каждое состояние — отдельный Node
с enter()/exit()/physics_update()). Реализованы состояния Idle, Run, Jump,
Fall, Land, Dash, Attack. StateMachine хранит текущее состояние и метод
transition_to(name) для переключения между ними.

Обнаружен и исправлен архитектурный нюанс: StateMachine нельзя запускать
автоматически в своём _ready(), т.к. Godot вызывает _ready() дочерних узлов
раньше родительских — @onready-поля Player (например, animated_sprite) ещё
не готовы в этот момент. Решение — явный метод StateMachine.start(),
вызываемый из конца Player._ready().

Комбо-атака увеличена с 3 до 4 шагов — при разбивке анимации light-атаки
(единый спрайт-лист на 40 кадров) выяснилось, что в ассете 4 отдельных
удара, а не 3. Комбо-шаг остаётся внутренней переменной одного состояния
Attack, а не отдельными состояниями на каждый удар — разные удары
физически ведут себя одинаково, различаются только анимацией и уроном.

Врагу добавлен hitstun: при получении урона (через уже существующий сигнал
health_changed) враг на stagger_duration (0.4с) не может атаковать и
преследовать, текущий замах прерывается. Реализовано через явные
переменные, не FSM — у врага пока всего 3 ветки поведения, полноценный
State Machine отложен до появления новых типов врагов.

Дважды за сессию встретился один и тот же баг: дублирование блока кода
в _physics_process (у enemy.gd и у player.tscn.gd) после ручной вставки —
приводило к двойному выполнению логики за один физический кадр (в т.ч.
ложной поломке двойного прыжка). Взято на заметку: после вставки кода
проверять функцию через Ctrl+F на предмет случайного дублирования.

Легаси-код движения/атаки/дэша (is_dashing, is_attacking, _process_movement,
_start_attack и т.д.) полностью удалён из player.tscn.gd — FSM единственный
источник истины о поведении игрока.
Следующие шаги по плану: (1) явный State Machine для движения, (2) геометрия 
тестового уровня, (3) лазанье по стенам, (4) визуал врага той же связкой.


### 17.08.2026 — Wall-climb состояние (лазание по стенам)

Добавлено новое состояние `WallClimb` в Player FSM. Обнаружение стены сделано
через штатный `is_on_wall()` + принадлежность коллайдера группе
`"climbable_wall"` — переиспользована физика CharacterBody2D вместо отдельного
RayCast2D/Area2D, в духе принципа "группы вместо жёстких путей".

Условие входа: Fall -> WallClimb, когда одновременно не на земле, is_on_wall(),
стена в группе climbable_wall и ввод направлен в сторону стены — без
последнего условия было бы случайное залипание при любом касании в прыжке.

Поведение в состоянии: вертикальная скорость клэмпится сверху новым
@export-параметром wall_slide_speed — сползание, а не зависание на месте.

Выход из состояния тремя путями: (1) отпускание/движение от стены -> Fall,
(2) приземление -> Idle/Run через is_on_floor(), (3) wall jump -> горизонтальный
+ вертикальный импульс от стены, переход в Jump/Fall.

Решена типовая проблема wall-jump: мгновенный повторный вход в WallClimb на
том же кадре из-за физического касания стены сразу после отталкивания.
Добавлен grace-таймер по аналогии с SAFETY_TIMEOUT-паттерном из Hurt —
блокирует повторный вход в WallClimb от той же стены короткое время после
wall jump.

can_be_interrupted() не переопределён, WallClimb наследует default true —
урон во время сцепления прерывает в Hurt, что физически логично.

Реализовано состояние Hurt в FSM игрока — первый пункт roadmap выполнен.

Архитектурное решение (Вариант Б): состояния сами решают, можно ли их
прервать. State.can_be_interrupted() -> bool, по умолчанию true (safe by
default). AttackState переопределяет: прерываем только в первой половине
timer (timer > attack_duration / 2.0) — удар, "закоммиченный" во второй
половине замаха, урон не прерывает.

HealthComponent эмитит отдельный сигнал damaged(amount), не совпадающий с
health_changed — семантически разные вещи (health_changed сработает и от
лечения в будущем, damaged — только от урона). Player слушает damaged,
проверяет current_state.can_be_interrupted() и либо делает
transition_to("Hurt"), либо игнорирует.

HurtState завершается по сигналу animated_sprite.animation_finished
(CONNECT_ONE_SHOT), а не по ручному таймеру — единый источник правды о
длительности состояния (сама анимация). Добавлен SAFETY_TIMEOUT (1 сек)
как защита от софтлока, если анимация не доиграет штатно (опечатка в
имени, забытый Loop=off и т.д.) — паттерн "сигнал + защитный таймаут".

Важный нюанс StateMachine.transition_to(): если запросить переход в
состояние, которое уже активно (совпадает по имени), метод молча
выходит без вызова enter(). Значит повторный урон, полученный уже в
Hurt, НЕ продлевает стан и не перезапускает нокбэк. Осознанно оставлено
как есть; если понадобится "продлевающийся стан" — переделывать здесь.

Ассет-пак Black Knight (полный архив, не то, что уже импортировано в
проект) содержит: Hurt (6 кадров), Death (9 кадров), Parry (3 листа),
Roll (12 кадров), Heavy attacks (3 листа, разное число кадров: 20/9/16).
Все на сетке 128x64 px/кадр, как и уже импортированные анимации.
Понадобится для следующих пунктов roadmap.

Побочный фикс: SHADOWED_GLOBAL_IDENTIFIER — параметр с именем max
(совпадает со встроенной функцией max()) стал жёсткой ошибкой в Godot
4.7.1. Переименован в max_health в HUD.gd и player.tscn.gd (сигнал
health_changed(current, max_health)).

Death-состояние сознательно отложено на отдельную сессию — оно завязано
на arena.gd._on_player_died() -> get_tree().paused = true, и просто
"добавить анимацию" недостаточно: нужно решить, как доиграть анимацию
смерти до паузы дерева (process_mode у AnimatedSprite2D и т.д.).

Дальше по плану: архитектура процедурной генерации уровня из комнат-шаблонов
(room-based generation по образцу Dead Cells / Rogue Prince of Persia) —
спроектировать формат комнаты с размеченными коннекторами входа/выхода,
создать 3-4 комнаты-шаблона, написать генератор, который их выбирает и
соединяет в случайный уровень при запуске. После этого — FSM для врага
(первый моб временно переиспользует модель игрока-заглушку).

### 29.08.2026 — Синхронизация тайминга атак с анимацией, честный урон по касанию, буфер ввода

Обнаружен и исправлен каскад из трёх связанных багов, всплывших после введения
Heavy Attack:

1. **Урон с лёгкой атаки пропадал** — `current_attack_damage` выставлялся
   только в `heavy_attack_state.enter()`, но не в `attack_state.enter()`.
   Light-атака била на 0 урона. Добавлена симметричная строка
   `actor.current_attack_damage = actor.attack_damage`.

2. **Длительность состояния атаки была оторвана от реальной анимации.**
   `attack_duration` (0.15с) и `heavy_attack_duration` (0.4с) — произвольные
   константы, никак не связанные с реальной длиной клипа в SpriteFrames
   (0.75-0.92с для лёгких ударов, 1.14-2.71с для тяжёлых). Стейт обрывал
   анимацию на середине и перекидывал в Idle/Run, чей enter() тут же
   перезаписывал кадр — отсюда ощущение "дёргается".

   Решение: в базовый `State` (`core/fsm/state.gd`) добавлен метод
   `get_animation_duration(sprite, animation_name)`, вычисляющий реальную
   длительность из `frame_count / animation_speed`. Оба attack-стейта берут
   `duration` оттуда при входе в `enter()`, вместо хардкоженных экспортов.
   Мёртвые `@export var attack_duration` / `heavy_attack_duration` удалены
   из `player.tscn.gd`. Это устраняет саму возможность рассинхрона —
   длительность стейта теперь физически не может разойтись с ассетом,
   т.к. читается из него напрямую, а не дублируется вручную.

3. **Урон засчитывался по нажатию кнопки, а не по касанию оружием.**
   `attack_shape.disabled = false` стоял в самом начале `enter()` -
   хитбокс был активен всю атаку целиком, включая кадры до замаха.
   Добавлено окно активности хитбокса как доля от длительности анимации
   (`active_start_ratio` / `active_end_ratio`, `@export`, крутятся в
   инспекторе) - хитбокс включается/выключается в `physics_update()` по
   факту прохождения этой доли времени. У врага аналогичная проблема была
   уже решена через явные Windup/Active/Recovery стейты - для игрока
   выбран более лёгкий вариант (одно состояние + доля времени) вместо
   копирования 3-стейтовой структуры, т.к. полноценное проектирование
   разбивки атаки на фазы отложено до детальной проработки системы оружия
   (см. roadmap).

**Побочный эффект синхронизации длительности - сломался комбо.** Раньше
комбо "работало" только благодаря удаче тайминга: атака длилась 0.15с,
следующий клик почти всегда случайно попадал на тот кадр, когда стейт-машина
уже была в Idle/Run и слушала `Input.is_action_just_pressed`. С честной
длительностью (0.75-2.7с) поймать этот кадר кликом стало практически
невозможно - комбо не было по-настоящему реализовано, оно никогда не
проверяло ввод во время самой атаки.

Добавлен **input buffer**: `attack_buffer_timer` / `heavy_attack_buffer_timer`
на игроке (окно 0.2с), заполняются в `_physics_process` при любом нажатии
независимо от текущего состояния, читаются через
`consume_buffered_attack()` / `consume_buffered_heavy_attack()`. Все
проверки `Input.is_action_just_pressed("Attack"/"heavy_attack")` в
Idle/Run/Jump/Fall заменены на чтение буфера. Ключевое место - `_end_attack()`
в обоих attack-стейтах теперь тоже проверяет буфер и уходит в следующий удар
напрямую, минуя Idle/Run - именно это чинит комбо-цепочку, а не проверки в
состояниях покоя сами по себе.

**Осознанный побочный эффект архитектуры**: `jump`/`dash`/`parry` остались
на сыром `Input.is_action_just_pressed`, атаки - на буфере. Два стиля чтения
ввода одновременно в кодовой базе. Не унифицировано осознанно - паттерн
`buffer_*`/`consume_buffered_*` растягивается на любой другой инпут, если
там тоже проявится проблема "узкого окна приёма", но добавлять его
превентивно туда, где проблемы нет, не стали.

**Ещё один найденный и исправленный баг того же происхождения**:
`combo_reset_timer` тикал безусловно каждый кадр, включая время самой
атаки. Был откалиброван под старую длительность 0.15с (успевал пережить
удар), но с честной длительностью 0.75-0.92с таймер сброса (0.6с) успевал
обнулить `combo_step` **на середине текущего же удара**, до того как
`_end_attack()` успевал его прочитать - отсюда хаотичный, не по порядку,
проигрыш анимаций комбо. Исправлено: таймер сброса не тикает, пока
`state_machine.current_state.name == "Attack"` (аналогично для
heavy) - сброс комбо теперь честно считает паузу между ударами, а не
включает в себя время самого удара.

**Принцип на будущее, стоит держать в голове**: длительность анимации,
окно активности хитбокса и таймер сброса комбо - не независимые параметры,
это связанная система. Любое изменение одного требует ревизии остальных.

Hit-stop (следующий пункт по roadmap) сознательно отложен ещё на сессию -
решили сначала добить честный тайминг урona по касанию, чтобы не строить
hit-stop поверх момента урona, который всё равно скоро переедет.
